## 1. Описание проекта

Реализован top-down arena shooter в жанре Brotato-like. Игрок управляет персонажем на арене 800×600 пикселей, автоматически стреляя по ближайшему врагу. Цель — пережить 10 волн нарастающей сложности. После каждой волны предлагается выбор одного из трёх случайных улучшений.

Игра написана на **строгом C11** с использованием исключительно **Win32 API** и **GDI** для графики. Сторонние движки, библиотеки и C++-конструкции не используются.

## 2. Архитектура

Проект разделён на три файла согласно принципу разделения ответственности:

### `core.c` / `core.h` — игровая логика

Модуль не имеет зависимостей от Win32. Содержит:

- Структуру `GameState` — единственный объект, описывающий полное состояние игры: игрок, массивы врагов, пуль, гемов, фаза, счёт, волна.
- `Core_Init` — инициализация/сброс состояния.
- `Core_Update(gs, dt)` — главный тик: движение, коллизии, стрельба, спавн, проверка конца волны.
- `Core_SetDifficulty`, `Core_StartWave`, `Core_ApplyUpgrade` — управление фазами игры.

Коллизии реализованы как AABB (axis-aligned bounding box) по центру объектов. Стрельба — автоматическая по ближайшему врагу через `FindNearestEnemy`. Враги трёх типов (обычный, быстрый, танк) масштабируют HP в зависимости от номера волны.

### `ui.c` / `ui.h` — Win32-интерфейс и отрисовка

Модуль отвечает за всё взаимодействие с ОС:

- Создание и регистрацию оконного класса (`RegisterClassExA`, `CreateWindowExA`).
- Обработку Win32-сообщений (`WndProc`): `WM_DESTROY`, `WM_KEYDOWN`.
- Опрос ввода через `GetAsyncKeyState` — запись в `gs->input` без прямой передачи в логику.
- Двойную буферизацию: создаётся `CreateCompatibleDC` + `CreateCompatibleBitmap`, рендер идёт в back-buffer, затем одним `BitBlt` выводится на экран. Это исключает мерцание.
- Загрузку спрайта игрока через `LoadImageA` / `LR_LOADFROMFILE`.
- Отрисовку пяти экранов: меню, игра, апгрейд, смерть, победа.

**Ключевое правило:** `core.c` не знает о `HWND`, `HDC` и любых Win32-типах. Передача данных — только через указатель на `GameState`.

### `main.c` — точка входа и игровой цикл

Реализован цикл с фиксированным шагом обновления (1/60 сек):

```
QueryPerformanceCounter → вычислить dt → накопить в accumulator
while (accumulator >= FRAME_TIME) {
    UI_PollInput → Core_Update → accumulator -= FRAME_TIME
}
UI_Render
```

Защита от слишком большого `dt` (пауза, отладка): значения выше 0.1 сек обрезаются. `Sleep(1)` в конце итерации снижает нагрузку на CPU без потери отзывчивости.

## 3. Игровой цикл

Используется схема **fixed timestep with variable rendering**:

- Физика и логика обновляются строго по 60 тиков в секунду независимо от реального FPS.
- Рендер вызывается один раз за итерацию главного цикла.
- Время измеряется через `QueryPerformanceCounter` — разрешение порядка микросекунд, без зависимости от таймеров ОС.
- `SetTimer` и `WM_TIMER` не используются, как указано в требованиях.

---

## 4. Графика и GDI

- **Двойная буферизация** через `CreateCompatibleDC` предотвращает мерцание при перерисовке.
- **Спрайт игрока** загружается из `assets/player.bmp` через `LoadImageA` с флагом `LR_LOADFROMFILE`. При отсутствии файла выводится предупреждение, игра продолжает работу.
- **Враги и пули** отрисовываются примитивами GDI (`FillRect`, `Rectangle`), что снижает зависимость от внешних ресурсов.
- Все GDI-объекты (`HBRUSH`, `HPEN`, `HFONT`, `HBITMAP`, `HDC`) освобождаются через `DeleteObject` / `DeleteDC` / `ReleaseDC` после использования.

---

## 5. Трудности и решения

| Трудность | Решение |
|-----------|---------|
| Мерцание при отрисовке | Двойная буферизация через `CreateCompatibleDC` |
| Плавное движение при разных FPS | Фиксированный шаг обновления с аккумулятором `dt` |
| Разделение логики и Win32 | `GameState` как единственный интерфейс между модулями |
| Кодировка русских строк в MSVC | `RUSSIAN_CHARSET` в `CreateFontA`, файлы в UTF-8 with BOM |
| Утечки GDI при перезапуске | `UI_Destroy()` освобождает все ресурсы; повторная инициализация через `Core_Init` |
